Ranked Content Review: A Transparent Queue Built on the FlyRank Internship Dataset

Which pages should a reviewer open first when capacity is limited?

Locket51 · March 2026 slice · Repo

Abstract. This paper asks which content pages a reviewer with limited weekly capacity should open first. Using the FlyRank internship warehouse on month = '2026-03', I built a five-feature ranking under a client-grouped holdout, then re-audited it under a strict time-aware split with no overlap between the feature and label windows. The ranking model scored Precision@50 = 0.46 on a naive random split and 0.54 on a client-grouped split, but collapsed to 0.06 under strict separation — near the positive-class base rate — which shows that most of the earlier lift was within-month autocorrelation rather than predictive skill. As a decision-support deliverable, I therefore ship a transparent reason-coded review queue instead of a model, with a human-review process and a clearly stated no-automation list.

1. Introduction

A reviewer cannot inspect every page in a content inventory. That is the problem this paper addresses: given more candidate pages than review hours, how should the queue be ordered, and what evidence supports that ordering? The output is decision-support: a ranked list with reason codes that tells a human which pages to open first. It is not a claim that editing a page causes a recovery — establishing that would require an experiment this data cannot provide.

2. Data

All work uses the FlyRank internship warehouse on Hugging Face (FlyRank/internship-warehouse, build flyrank_pseudonymized_warehouse_release_v20260703), restricted to a single mid-panel month: month = '2026-03'. The primary table is fact_content_daily_performance, filtered to gsc_data_available IS TRUE. This slice contains 9,841,378 rows across 55 clients and 331,437 content items, covering 2026-03-01 through 2026-03-31.

Only 3,611,061 of those rows (36.7%) have GSC data available and 413,966 (4.2%) have GA4 data. Because GA4 coverage is thin, GA4-derived features are excluded. The final June 2026 _sample table is deliberately not used anywhere in development — it is the natural outcome window of any past→future label.

3. Methodology

Unit of analysis. One row per content item, summarised over a window inside March 2026.

Features (5). impressions_first_half, clicks_first_half, avg_position_first_half, ctr_first_half, days_with_impressions_first_half — all built from days 2026-03-01 to 2026-03-15.

Proxy label. is_declining — did second-half impressions fall below 70% of first-half impressions? This is a defined rule, not a future observed outcome. It is used as a Week-5 proxy so the modelling loop runs end to end; the Week-6 audit tests whether it holds up.

Baseline. A transparent rule from Week 4: 0.45·visibility + 0.30·position_opportunity + 0.25·decay_risk, with hand-picked weights.

Validation design. Three splits are compared on the same rows: (a) a naive random 80/20 split, (b) a client-grouped holdout (whole client_hash_id groups held out), and (c) a strict time-aware split with a 7-day feature window (03-01 to 03-07) and a non-overlapping 23-day label window (03-08 to 03-31), with client grouping still enforced.

Leakage checks. Six-question checklist run against the guide — features strictly before the decision point, no overlap between feature and label windows, no rebuilt product flags, no derived field that encodes the target, no related rows split across train/test, and testing on clients never seen in training.

4. Results

The same Random Forest is scored three ways on the same five features. The before/after shows how much of the earlier lift was an artefact of the split.

SplitROC AUCAverage precisionPrecision@50
BEFORE — naive random split0.6310.3010.460
AFTER — client-grouped holdout0.5760.3590.540
AFTER+ — time-aware + client-grouped0.5240.0310.060

Reading. Client grouping alone did not hurt the model — the naive random split was not the main leak. The strict time-aware split collapsed Precision@50 to 0.06 and ROC AUC to 0.524, near the base rate. That drop is the size of the within-month autocorrelation that the Week-5 design was carrying. The honest conclusion is that the model did not rank well on this slice under strict separation.

5. Limitations & honest framing

  • Single month, single slice. All numbers are on month='2026-03', 55 clients. They do not establish behaviour on the full warehouse or on other months.
  • Proxy label. is_declining is a rule-computed within-month proxy, not a future observed outcome. The Week-6 audit tests what that means.
  • No causal claim. A page on the queue is a candidate. Nothing here shows that editing a page causes recovery.
  • Search-only features. GA4 signals excluded because only 4.2% of rows have GA4 data.
  • Composite-metric caution. No FlyRank product score is used as a feature or a target.

6. Ranked recommendations

The shipped deliverable is a transparent reason-coded queue, not a model. Every page gets exactly one reason code, which maps to one action and one human owner.

Reason codeWhat it looks likeActionOwner
declining_visible_pageimp_first ≥ 500, second-half impressions fell ≥30%refreshContent editor
top10_low_ctravg position ≤ 10, CTR < 0.5%metadata_reviewSEO specialist
watchvisible but no specific patternmonitorReviewer spot-check
no_signallow visibility, no specific patterndropnot reviewed

What must not be automated

  • Auto-refreshing a page — the queue does not know the topic, brand voice, or internal links.
  • Auto-rewriting titles or metas — CTR alone is a weak signal.
  • Auto-pruning or merging — consolidation needs an editor who can see query overlap and business value.
  • Feeding the queue back into a model as if it were ground truth.

Monitoring and retrain triggers

  • Reason-code distribution drifts by more than 20% between months.
  • Precision@50 falls below the base rate on a new month under strict validation.
  • Client mix changes materially (re-fit the visibility normalisation).
  • Label definition changes (any future-window version requires re-validating every feature).

7. Reproducibility

Every result in this paper is regenerated by the notebooks in the repo, under work/notebooks/:

  • w01_research_question.ipynb — framing and lane
  • w02_ml_task_framing.ipynb — task type and unit of analysis
  • w03_data_contract.ipynb — contract, verification queries, leakage trap
  • w04_baseline_score.ipynb — signal checks and the baseline rule
  • w05_model.ipynb — Logistic Regression / Random Forest / Gradient Boosting
  • w06_validation_audit.ipynb — three-split before/after, leakage audit, claim rewrite
  • w07_action_playbook.ipynb — the queue, reason codes, exports

Metrics receipts live in work/outputs/*.json. The queue CSV is regenerated on every run of w07. Raw client, URL, and query fields do not exist in the release and are not used here.
